# A3：N-gram 投机解码的开环 SLO 容量边界（vLLM 0.29.0，2026-10-10）

> **本次结论**：在这台 RTX 4090、eager 服务配置和 50:50 合成负载的 3 × 60 秒正式窗口里，**2.4 req/s 是最高通过的已测档，2.6 req/s 是最低失败的已测档**。失效区间按本次网格记为 **(2.4, 2.6] req/s**。这是示例逐请求 SLO 的实验边界，不是生产最大 QPS、硬件极限，也不是调大投机 token budget 后的结果。
>
 旧版 R570/vLLM 0.18.0 探索结果、2026-10-09 的 v0.29.0 容量网格，以及 A1/A2 的不同容器结果均单独看；本报告只汇总本容器的 N-gram 档位，不构造跨容器严格配对。

## 做了什么

按 [A3 预注册协议](spec_ngram_capacity_boundary_protocol_20261010.md)先复测 2.0，再升到 2.4、2.8；2.8 首次完整失败后，在通过档与失败档之间补测 2.6。由于已有失败档，按协议未继续升至 3.2。每档单独调用客户端，先 10 秒预热，再做 3 次 60 秒正式轮，轮间等请求排空。预热不计入表格和 SLO 判定。

## 学到什么

1. **吞吐还在升，合格服务能力已下降。** 2.4→2.6→2.8 req/s 的输出吞吐中位数为 573.525→612.907→621.713 tok/s，但 SLO goodput 为 2.2403→2.0953→0.4918 req/s。2.8 虽然所有请求最终成功，三轮合计仅 **104/504** 条按时完成。若只看成功率或 token/s，会错过业务侧的容量悬崖。
2. **先触发的是排队和 TTFT，而非 KV 抢占。** 2.6 的 Running 已碰到 `max-num-seqs=8`，Waiting 峰值 3–4、到达窗末仍有 1–3 条等待；2.8 的 Waiting 峰值 14–15、窗口末仍有 13–14 条。两档 KV 峰值仅约 2%，`num_preemptions` 增量始终 0。服务端队列时间均值从 2.4 的约 2 ms 上升到 2.6 的 0.34–0.63 s、2.8 的 2.40–2.67 s。故本轮 Waiting 不能解释成 KV 抢占。
3. **投机接受行为在四档大致稳定。** 服务端平均接受长度三轮中位数分别为 1.9828、1.9925、1.9869、1.9874。没有看到接受长度随负载升高而崩塌；排队和并发上限与 TTFT 恶化同时出现。这里的观察不足以独立量化 GPU 算力、调度 token budget 和其他资源各自的贡献。
4. **2.4 仍有余量迹象，2.6 已不满足严格逐请求 SLO。** 2.4 虽偶有 Waiting=1，但每轮到达窗末 Waiting=0、排空约 4.2 s，与最后几条在飞请求的自然收尾相符。2.6 预热全达标，正式轮却从 155/156 变为 112/156，说明短预热不能替代正式窗口，也不能把本次 0.2 req/s 网格当成精确的物理极限。

## 验收与局限

- 4 档 ×（1 次预热 + 3 次正式轮）全部完成；每轮计划数、派发数、成功数一致，未完成数 0，dispatch lag P95 ≤0.5 ms、指标轮询错误 0、无安全停止。正式请求共 **1764** 条，其中 **1299** 条满足示例逐请求 SLO。服务实际配置由启动日志核对；本地原始文件与云端 SHA-256 **10/10 一致**。
- **只定义本次 60 秒合成负载的已测边界。** 三次重复能暴露一定波动，但不足以证明小时级稳态、真实流量尾延迟或生产容量。尤其 2.6 的达标数在三轮间差异较大；真实边界也不必严格单调。
- 只测 `repeat/count` 各半、256 token、确定性到达、eager、N-gram 4 草稿 token，且 `max-num-batched-tokens=4096` 保留投机槽位警告。调整负载形状、执行模式、批次上限或投机配置可能移动边界，需要另立单变量实验。未对本容器重新测 baseline，不能用 A1 的不同容器数据计算严格加速倍数。
- 本轮 2.4 的到达窗末无 Waiting，排空尾巴未随重复单调增长，故未触发预注册协议中的 3 × 120 秒稳定性核查。若将 2.4 req/s 用于实际容量规划，仍需延长窗口并加入真实流量波动。
- 实验后通过 SSH 停止 vLLM；`/health` 不再响应，`nvidia-smi` 显存为 **0 MiB**。这只确认服务停止，**不代表云平台实例已关机或停止计费**；实例状态需在平台控制台单独确认。
