# N-gram 投机解码 baseline vs ngram：vLLM 0.29.0 / RTX 4090 正式对照（2026-10-09）

> **版本边界**：这是 Phase 5 #5 的 **vLLM 0.29.0 正式实验**（驱动 590.44.01），与 [R570 / v0.18.0 探索性对照](spec_ngram_exploratory_r570_v018_20261009.md)分属不同版本与驱动，**数字不得互推**。本页第 4 节只在"结论是否同向"这一层对照。
>
> **本页的核心发现**：在这组负载和配置下，投机解码的每步耗时接近基线，收益主要来自"每步吐出更多 token"。见第 3 节第 2 条。

## 为什么测

投机解码的思路是"猜几个 token，然后一次并行验证"。猜中的话，一次前向就能推进多个 token。N-gram 是最轻量的一种草稿来源：不加载草稿模型，直接在**已有上下文里做 n-gram 查表**。本实验用两种刻意对立的负载形状，检验它到底在什么条件下有用、收益来自哪里。

- **repeat 形状**（约 568 tokens 的周期性文本，如"蓝色风车缓缓转动，白色小船轻轻靠岸。"反复）：n-gram 查表几乎必然猜中——这是**上限**。
- **count 形状**（约 68 tokens 的数数任务，无重复结构）：n-gram 几乎无从查起——这是**下限**。

两个形状跑在同一组服务上，避免换服务引入的漂移。

## 正式结果

### 1) 收益与形状强相关：同一个开关，两种命运

3 次正式轮中位数：

| 形状 / 并发 | baseline 吞吐 (tok/s) | ngram 吞吐 (tok/s) | 变化 | baseline 端到端 (s) | ngram 端到端 (s) | 变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **repeat** c=1 | 45.873 | **203.063** | **+342.7%** | 5.5547 | **1.1685** | **−79.0%** |
| **repeat** c=8 | 331.732 | **1185.611** | **+257.4%** | 6.1608 | **1.6294** | **−73.6%** |
| count c=1 | 45.879 | 57.362 | +25.0% | 5.4990 | 4.4083 | −19.8% |
| count c=8 | 351.833 | 405.615 | +15.3% | 5.7671 | 4.6494 | −19.4% |

TTFT 基本不动（repeat c=1：0.0797 → 0.0795；count c=8：0.1015 → 0.1074）——**投机解码不加速 Prefill**，它只在 Decode 段起作用。

组内离散度极小：repeat c=8 吞吐 baseline [326.353, 331.732, 331.938] vs ngram [1183.427, 1194.143, 1185.611]，**两组区间完全不相交**。

### 2) 每步耗时接近——收益主要来自"每步多吐 token"

从原始 SSE 内容事件时间戳近似计算每步墙钟时间。本组投机请求的事件数与「输出 token 数 − 接受 token 数」逐数吻合：repeat c=1 为 256 − 204 = 52，count c=1 为 256 − 57 = 199。因此**在这次 v0.29.0 流式实现与负载中**，内容事件可作为步级代理；仅凭计数吻合不能证明 SSE API 在所有版本、配置或中间代理下都保证一事件一引擎步。

| 配置 | 每步耗时 | 每步 token 数 |
| --- | ---: | ---: |
| baseline repeat c=1 | 21.52 ms | 1.00 |
| baseline repeat c=8 | 22.29 ms | 1.00 |
| baseline count c=1 | 21.37 ms | 1.00 |
| baseline count c=8 | 22.17 ms | 1.00 |
| ngram repeat c=1 | 21.34 ms | **4.92** |
| ngram repeat c=8 | 22.55 ms | **4.92** |
| ngram count c=1 | 21.39 ms | 1.29 |
| ngram count c=8 | 23.83 ms | 1.24 |

**八个配置的每步耗时都落在 21.3–23.8 ms 区间**，最大偏离 +7.5%（出现在 count c=8）。也就是说：验证 4 个草稿 token **几乎没有让每一步变贵**（批大小为 1 时甚至完全相同，21.34 vs 21.52 ms）。于是每 token 耗时 = 每步耗时 ÷ 每步 token 数：

| 配置 | 每 token 解码耗时 (ms) | 解码加速比 | ≈ 每步 token 数 |
| --- | ---: | ---: | ---: |
| repeat c=1 | 21.52 → **4.27** | **5.04×** | 4.92 |
| repeat c=8 | 22.29 → **4.51** | **4.94×** | 4.92 |
| count c=1 | 21.37 → 16.61 | 1.29× | 1.29 |
| count c=8 | 22.17 → 17.87 | 1.24× | 1.24 |

**解码加速比几乎精确等于每步 token 数**——这就是本实验最干净的一条因果链。

端到端加速比（4.43× / 3.57× / 1.25× / 1.15×）比解码加速比小，**未被投机加速的 Prefill 与其他端到端开销**会稀释收益：repeat c=1 的 0.08 s TTFT 在 ngram 的 1.26 s 总时长里占 6%，而 repeat c=8 的 0.478 s TTFT 在 1.727 s 里占 **27.7%**。这些占比支持这一解释，但没有单独隔离所有开销。

### 3) 接受率：上限 100%，下限 6%

服务端自己的统计（客户端从 Prometheus 计数器逐轮取差，与 `metrics.py:120` 每 10 s 打印的日志同源）：

| 形状 / 并发 | 草稿 token | 接受 token | 接受率 | 平均接受长度 | 逐位接受率 |
| --- | ---: | ---: | ---: | ---: | --- |
| repeat c=1 | 204 / 204 / 204 | 204 / 204 / 204 | **1.0000** | **5.000** | 1.000, 1.000, 1.000, 1.000 |
| repeat c=8 | 1632 ×3 | 1632 ×3 | **1.0000** | **5.000** | 1.000, 1.000, 1.000, 1.000 |
| count c=1 | 775 / 835 / 803 | 57 / 42 / 50 | 0.0735 / 0.0503 / 0.0623 | 1.294 / 1.201 / 1.249 | ~0.26, 0.02, 0.005, 0.005 |
| count c=8 | 6516 / 6448 / 6472 | 383 / 398 / 389 | 0.0588 / 0.0617 / 0.0601 | 1.235 / 1.247 / 1.240 | 0.205, 0.020, 0.005, 0.005 |

repeat 形状**三轮全部 100% 接受、逐位都是 1.000**——周期性文本下 4 个草稿 token 全中，平均接受长度恰好 5.000（4 个接受 + 1 个验证步自带的 bonus token）。

count 形状的第 1 位接受率约 21%，第 2 位掉到 2%，第 3/4 位约 0.5%——**阶梯式衰减**说明 n-gram 偶尔能接上一个词，但延续不了。

### 4) 输出正确性：72/72 逐字节相同

投机解码在数学上应当是**无损**的（草稿只是候选，验证由目标模型做）。本实验直接验证：两组所有 72 条成功请求的输出文本 SHA-256 **逐一相同**，`completion_tokens` 均等于 256。

## 学到什么，怎样判读

1. **接受长度是关键，但不能脱离每步成本。** 本组每步耗时接近，因此接受长度 5.000 对应约 4.9–5.0× 的解码加速，1.24 对应约 1.24×。评估其他投机方案时还要同时测验证步耗时、额外显存和调度开销；只看接受长度不能预判其收益上限。

2. **本组 4-token 草稿的额外步成本较小。** 每步耗时基线 21.5/22.2 ms，投机后 21.3–23.8 ms。显存带宽受限是一个合理机制解释，但本实验没有直接测 GPU 带宽、算力或 kernel 组成，不能据此断言所有负载都由带宽主导。

3. **本组端到端收益小于解码收益。** 同一个约 4.94× 的解码加速，在 c=1 变成 4.43× 端到端，在 c=8 变成 3.57×；对应 TTFT 分别约 0.080 s 和 0.478 s。未被投机直接加速的 Prefill 与其他开销会稀释端到端收益；更大 Prefill、短输出时尤其应单独验证，而不能把解码加速比直接当业务加速比。

4. **低接受率也可能有收益。** count c=8 接受率约 5.9%，每步 token 数从 1.00 升到 1.24，本组吞吐仍提高 15.3%。是否值得开启投机，需要把接受长度带来的推进量与验证步成本、显存和业务负载一起比较；低接受率并非自动无效，也并非一定"纯赚"。

5. **重复结构是 n-gram 的"免费午餐"，也是最容易被误读的场景。** 100% 接受率来自提示词本身的周期性——现实里代码补全、模板化文档、结构化 JSON 输出确实有大量重复，但**闲聊和自由创作几乎没有**。拿 repeat 的 3.4× 去承诺线上收益会是严重的过度承诺；count 的 15% 才是"无重复文本"这一端的参考值，而真实负载在两者之间。

## 验收与局限

- 2 形状 × 2 并发 × (1 预热 + 3 正式) = 16 次运行全部成功，两组各 96 条正式请求均生成 256 tokens；两组 `preemptions_delta` 均为 0。配置证据取自启动日志 `non-default args` 行：ngram 组含 `'speculative_config': {'method': 'ngram', 'num_speculative_tokens': 4, 'prompt_lookup_min': 1, 'prompt_lookup_max': 4}`，baseline 组**该键不出现**；`enable_prefix_caching: False` 两组相同。
- **服务端有一条真实警告（必须交代）**：`max_num_scheduled_tokens is set to 4096 based on the speculative decoding settings. This may lead to suboptimal performance. Consider increasing max_num_batched_tokens to accommodate the additional draft token slots, or decrease num_speculative_tokens.` 本实验固定 `max-num-batched-tokens=4096`，与投机所需的额外草稿槽位相同，**因此本页的收益数字很可能是偏低的下界**，而不是调优后的上限。这一点未被测试。
- **KV 池有微小差异**：ngram 组 143,536 tokens vs baseline 143,728（−192 tokens，约 0.13%），来自投机配置对显存 profiling 的影响。对 568-token 级请求的对照无实质影响，但记录在此以免读者误以为两组显存完全一致。
- **局限一：全部在 `--enforce-eager` 下完成**（无 torch.compile / CUDA Graph）。投机解码与 CUDA Graph 的交互（尤其是多 token 验证的 shape 变化）未测，默认模式下收益可能不同。
- **局限二：负载是合成的两个极端形状**，输出长度固定 256 tokens。真实流量的接受率取决于文本重复度，本页给出的是上下限而非点估计。**两个形状各自的 prompt 内部高度重复**（同一个 568-token 模板反复用），跨请求的前缀复用被 `--no-enable-prefix-caching` 切断，避免与 Prefix Cache 混淆——这是刻意的单变量控制。
- **局限三：`client_decode_tail_per_token_s` 是"解码总时长 ÷ (输出 token 数 − 1)"的均值口径**，不是事件间隔的中位数；在投机下它与"每步耗时 ÷ 每步 token 数"一致（已验证），但不要把它读成"相邻两个 SSE 事件的间隔"。
- **局限四：只测了 `num_speculative_tokens=4` 与 `prompt_lookup_min/max=1/4` 这一组参数**，未做草稿数与查表窗口的扫描；`prompt_lookup_min=1` 是刻意选的激进设置（vLLM 0.29 默认为 5，见 `vllm/config/speculative.py:1148`），它让 count 这种无重复文本也产生大量低质量草稿。调小草稿数可能在 count 形状上更好、在 repeat 上更差。
