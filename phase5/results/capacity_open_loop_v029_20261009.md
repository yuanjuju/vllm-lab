# 开环容量网格：baseline vs ngram 投机解码（vLLM 0.29.0 / RTX 4090，2026-10-09）

> **版本边界**：本页两组均为 **vLLM 0.29.0 正式实验**（驱动 590.44.01），不涉及 v0.18.0 数据。
> **配套报告**：[spec_ngram_v029_20261009.md](spec_ngram_v029_20261009.md)（闭环形状对照）解释了本页出现差异的机制。本页回答的是另一个问题：**在持续到达压力下，系统的容量边界在哪里。**

## 为什么测

闭环实验（固定 8 并发）只能说明"某个负载下谁快"，不能说明"能扛多高的到达率"。开环实验以**固定速率持续投递**（不看服务是否忙），才能暴露容量边界：当到达率超过服务能力时，队列会累积、延迟会爆炸——而闭环测试永远看不到这一点，因为它会自动"背压"。

两个条件除服务参数外完全一致，同一 `experiment-id` 保证提示词构造逐字相同：

- **baseline**：`--no-enable-prefix-caching`（无投机）
- **ngram**：同上 + `--speculative-config '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_min":1,"prompt_lookup_max":4}'`

## 实验条件与复现

| 项目 | 固定条件 |
| --- | --- |
| 实例 / 环境 | 云端单卡 RTX 4090（49140 MiB）；驱动 590.44.01；vLLM 0.29.0 |
| 服务参数 | `max-model-len=4096`、`gpu-memory-utilization=0.75`、`max-num-seqs=8`、`max-num-batched-tokens=4096`、`--enforce-eager`、仅监听云端 `127.0.0.1:8000` |
| 到达过程 | 确定性周期开环，**无客户端并发上限**；速率 1.6 / 1.8 / 2.0 req/s |
| 每轮结构 | 预热 10 s，随后 3 次正式窗各 60 s；波形在窗间排空 |

## 正式结果

### 1) 两组命运完全不同：一组排队到爆，一组全程零排队

3 次正式窗（baseline 的 1.8 因安全停止只有 1 次）：

| 速率 | 组 | TTFT P95 (s) | 排队峰值 | 运行峰值 | in-flight 峰值 | SLO 达标率 | 达成吞吐 (tok/s) |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1.6 | baseline | **9.4331** | **14** | 8（上限） | 22 | **0.1667** | 330.2 |
| 1.6 | **ngram** | **0.0951** | **0** | 6 | 6 | **1.0000** | 385.3 |
| 1.8 | baseline | **11.1754** | **17** ⚠ | 8（上限） | 25 | 0.1096 | 311.5 |
| 1.8 | **ngram** | **0.0974** | **0** | 7 | 7 | **1.0000** | 431.3 |
| 2.0 | baseline | — **未运行**（协议规定安全停止后不再升级） | | | | | |
| 2.0 | **ngram** | **0.0969** | **0** | 7 | 7 | **1.0000** | 477.3 |

**在唯一两组都跑完的 1.6 req/s 上**：

- TTFT P95：9.4331 s → 0.0951 s，**快约 99 倍**
- **SLO 合格吞吐（goodput）：0.2150 → 1.5050 req/s，7.0 倍**
- SLO 达标率：16.7% → 100%

### 2) baseline 在 1.6 req/s 已饱和——三个独立指纹同时出现

| 指纹 | 观测 |
| --- | --- |
| 队列累积 | 排队峰值 14（1.6）/ 17（1.8），运行数顶在 `max-num-seqs=8` 上限 |
| 到达结束后的排空 | 到达窗 60 s 结束后仍需 **14.4 s** 才排空（ngram 仅 3.7–4.4 s，且那是最后几条在飞请求的正常收尾） |
| 吞吐与到达率脱钩 | 投递 96 条全成功，但达成 330.2 tok/s 对 409.6 tok/s 的需求——**缺口 19%**，且三次窗口数值几乎相同（330.2 / 330.2 / 329.3），是稳态饱和而非抖动 |

由此反推 baseline 在此负载下的实际容量：`330.2 tok/s ÷ 256 tokens/请求 ≈ 1.29 req/s`。**这低于网格最低档 1.6 req/s**——网格的下界设得太高，baseline 的 SLO 悬崖没有被定位到（见局限一）。

### 3) 1.8 那一档的 311.5 tok/s 不能当作容量读数

1.8 req/s 的正式窗触发了安全停止（Waiting 17 > 16）：客户端**停止投递**，只派出 73/108 条，因此到达窗末尾队列已排空（`waiting_near_arrival_end = 0`，`drain = 0.00 s`）。这个 311.5 tok/s 是在一个"后半段无压力"的窗口上算出来的，**不反映饱和吞吐，也不说明"速率升高后吞吐反而下降"**。真正的容量读数用 1.6 档的 330.2 tok/s。

### 4) ngram 在 2.0 req/s 仍未触顶

ngram 三档全部 `排队峰值 = 0`、`SLO 达标率 = 1.0`，`in-flight` 峰值只有 6–7（未触及 8 的上限）。它在 2.0 req/s 达到 477–481 tok/s 而毫无排队，说明容量上限**还在更高处**，本网格未测到。

用配套闭环实验（8 并发）的混合容量作参照：ngram 在 8 并发下 repeat 形状 1185.6 tok/s、count 形状 405.6 tok/s，50:50 混合均值约 **796 tok/s ≈ 3.1 req/s**，可作为 ngram 容量的上界估计；下界是实测的 2.0 req/s。**即 ngram 容量在 2.0–3.1 req/s 之间，约为 baseline（1.29 req/s）的 1.6–2.4 倍。**

### 5) 跨实验核对：闭环的接受率预测了开环的接受率

混合负载的投机统计可与闭环实验互相验证。用闭环 A/B 的每请求接受数据（每形状 60 条）预测 2.0 req/s 混合窗：

| 量 | 预测（用 A/B c=1） | 预测（用 A/B c=8） | 实测 |
| --- | ---: | ---: | ---: |
| 草稿 token 总数 | 15,120 | 15,210 | **15,353** |
| 第 0 位接受 | 5,700 | 5,625 | **5,499** |
| 第 1 位接受 | 3,300 | 3,300 | **3,296** |
| 第 2 位接受 | **3,120** | **3,120** | **3,120** |
| 第 3 位接受 | **3,120** | **3,120** | **3,120** |
| 平均接受长度 | 2.0079 | 1.9970 | **1.9793** |

第 1–3 位几乎逐数吻合（第 2/3 位完全相同），接受长度误差 1.4%。**说明 ngram 的接受行为在不同负载形状与并发下是稳定的、可预测的**；也能反过来确认本页与闭环用的是同一套提示词构造。第 0 位实测略低于预测（5,499 vs 5,625–5,700，低 2–3.5%），可能与开环提示词里带了到达序号有关，未深究。

## 学到什么，怎样判读

1. **"能跑多快"和"能扛多少"是两个问题，必须分别测。** 闭环实验里 baseline 8 并发跑 331.7 tok/s 看着正常；开环一加压就暴露它只能撑 1.29 req/s，超过就排队到 9.4 s TTFT。**闭环测试自带背压，永远不会告诉你容量边界在哪。**

2. **饱和有三个可独立观测的指纹，别只看延迟。** 排队数顶到并发上限、到达结束后留下十几秒排空、达成吞吐与到达率脱钩——本实验三个同时出现。只看 TTFT 会把"服务器变慢"和"队列变长"混为一谈。

3. **SLO 达标率是最贴近业务的单一指标。** 1.6 req/s 下 baseline 的原始吞吐是 ngram 的 86%（330 vs 385 tok/s，差距不大），但 **goodput 只有 1/7**（0.215 vs 1.505 req/s）——吞吐看着差不多，实际"合格地产出"差了 7 倍。**报告容量时只给吞吐会严重误导容量规划。**

4. **安全停止起作用了，而且它保护了数据质量。** Waiting 17 触发停止后，1.8 档的数据变成"半截窗口"，本页明确标注它不可用作容量读数。**如果不设这个护栏，被测系统会在长时间过载下出现抢占与 OOM，那组数据反而更不可信。**

5. **容量上限的估计可以跨实验交叉验证。** 用闭环 8 并发的混合容量推 ngram 约 3.1 req/s、用开环实测确认至少 2.0 req/s，两个独立来源给出 2.0–3.1 的区间。**单次扫描的边界往往是"没测到"，而不是"测到了"，用另一组实验补上界比继续加密扫描更省成本。**

## 验收与局限

- ngram 组 3 档 × (1 预热 + 3 正式) 全部完成，共 12 次运行、324 条正式请求全部成功；baseline 组完成 1.6 档全部 + 1.8 档 1 次正式窗（因安全停止截断）。两组配置证据取自各自启动日志 `non-default args` 行；两组均 `enable_prefix_caching: False`、`max_num_seqs: 8`。
- **局限一：baseline 的 SLO 悬崖没有被定位。** 网格最低档 1.6 req/s 已超过 baseline 容量（1.29 req/s），因此只知道"容量 < 1.6 req/s"，不知道它在 0.8 或 1.2 处是否仍满足 SLO。协议在写定速率档位时没有先做容量预估，这是设计缺陷；要定位需补跑 0.6 / 1.0 / 1.4 档。
- **局限二：ngram 的容量上限同样未测到**（2.0 req/s 零排队）。第 4 节的 3.1 req/s 是用**另一组实验**（闭环 8 并发）的混合容量做的外推估计，不是本网格的实测点；两个实验的并发条件不同，该数字只能当量级参考。
- **局限三：只有 3 个速率档、每档 3 次 60 s 窗口，且只测到 2.0 req/s。** 容量是"负载形状的函数"——本页固定 repeat/count 50:50、输出 256 tokens。换形状（如全 count、或输出 2048 tokens）会显著改变容量绝对值，本页结论不可外推到其他形状。
- **局限四：全部在 `--enforce-eager` 下完成**（无 torch.compile / CUDA Graph），且 ngram 组带有 `max_num_batched_tokens` 与投机槽位相等的服务端警告（见[配套报告](spec_ngram_v029_20261009.md)的局限二），其绝对容量很可能被低估。
- **局限五：`达成吞吐` 的分母是"到达窗 + 排空"总时长**（脚本定义如此），因此组间比较须在同一口径下进行。本页所有吞吐数字同口径；这也是为什么 ngram 各档的达成值低于投递值约 7%——那是请求收尾的正常排空，不是容量不足（其排队峰值恒为 0）。
- **局限六：安全停止阈值 Waiting > 16 高于 baseline 的实际稳态排队（14）**，所以 1.6 档得以跑完三轮；若阈值设得更低，1.6 档也会被截断。阈值的选择直接决定了哪些档位能拿到完整数据。
