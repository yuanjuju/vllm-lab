# Prefix Cache 开/关：R570 / vLLM 0.18.0 探索性对照（2026-10-08）

> **版本边界**：这是当前 R570 节点上临时 CUDA 12.8 环境的教学实验，**不计入 Phase 5 B1（vLLM 0.29.0）完成状态**。不能与旧版 0.29.0 基线拼接，也不能把此处收益推广到其他负载或硬件。

## 为什么测

已有 Phase 3 结果证明共享前缀有命中，但“命中”与“性能收益”是两件事。这里在相同模型、提示词和输出长度下，单独切换 Prefix Cache，观察客户端 TTFT、整批输出吞吐和服务端指标是否一致。若命中确实省掉了大段重复 Prefill，最直接的现象应是 TTFT 缩短；Decode 的每 token 间隔不一定有同等幅度的变化。

## 实验条件与复现

| 项目 | 固定条件 |
| --- | --- |
| 实例 | 单卡 RTX 4090 48GB；宿主机驱动 570.124.06 |
| 环境 | 项目内 `.venv-cu128-vllm018`；vLLM 0.18.0、PyTorch 2.10.0+cu128；不触碰原 `.venv` |
| 模型 | 本地 Qwen3-8B，BF16；`max-model-len=4096` |
| 服务参数 | `gpu-memory-utilization=0.75`、`max-num-seqs=8`、`max-num-batched-tokens=4096`、`--enforce-eager`、仅监听云端 `127.0.0.1:8000` |
| 唯一开关 | 开启组默认 `enable_prefix_caching=True`；关闭组加 `--no-enable-prefix-caching`；均由启动日志的配置行验证 |
| 负载 | 每轮先发 16-token prime 建立前缀；接着 4 个并发探针，共享约 1423-token 输入，每个固定输出 64 tokens；之后发 16-token 改变前缀的对照请求。采样 `temperature=0`、关闭 thinking |
| 重复与链路 | 各组先独立预热一次，再正式重复 3 次；每轮前缀标记不同，避免跨轮复用；客户端运行在云端本机，走 loopback，不含 Mac↔云端 SSH 往返 |

同一 `experiment-id` 使两组对应轮次的 prompt SHA-256 一致。每组 4 个探针 × 3 轮，正式探针 12/12 成功且均生成 64 tokens；prime、改变前缀对照和预热也成功。每轮的 4 个请求同时释放；probe 指标快照在 prime 后、改变前缀对照前采集，避免将两者的命中数算进探针。

## 正式结果

下表每项是**同轮 4 个并发探针**的统计；TTFT P50/P95 是客户端首个有内容的 SSE 事件，吞吐是 `4 × 64 / 整批完成秒数`，并非纯 Decode 速度。预热轮不参与统计。

| Prefix Cache | 正式轮 | 客户端 TTFT P50 / P95 (s) | 整批耗时 (s) | 输出吞吐 (tok/s) | 命中 / 查询 tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| 开 | 1 | 0.0812 / 0.0813 | 1.3597 | 188.279 | 5568 / 5692 |
| 开 | 2 | 0.0861 / 0.0865 | 1.3610 | 188.103 | 5568 / 5692 |
| 开 | 3 | 0.0830 / 0.0834 | 1.3531 | 189.199 | 5568 / 5692 |
| 关 | 1 | 0.5426 / 0.5647 | 1.7808 | 143.756 | 0 / 0（计数未启用） |
| 关 | 2 | 0.5512 / 0.5808 | 1.8196 | 140.692 | 0 / 0（计数未启用） |
| 关 | 3 | 0.5495 / 0.5769 | 1.8326 | 139.695 | 0 / 0（计数未启用） |

三轮中位数：开启 vs 关闭，客户端 TTFT P50 为 **0.0830 vs 0.5495 s**（此负载下降约 84.9%），输出吞吐为 **188.279 vs 140.692 tok/s**（此负载提高约 33.8%），整批耗时为 **1.3597 vs 1.8196 s**。开启组查询 tokens 的命中比均为 97.82%；每个探针约 1423 输入 tokens，其中 1392 被复用。改变前缀的对照每轮仅命中 16/1419，可能来自共同聊天模板/块，不应描述为“绝对零命中”。关闭组的计数是 0/0，**命中率无定义**，不是“0% 命中率”的测量。

辅助指标：开启/关闭的服务端 TTFT **均值的三轮中位数**为 0.0736/0.4555 s，方向与客户端一致；服务端 ITL 均值为 0.0188/0.0205 s。两组各轮 Running 采样峰值 4、Waiting 采样峰值 0、`num_preemptions` 增量 0；KV Cache 使用率采样峰值约 1.23%/4.14%。队列直方图 `sum` 在本脚本四位小数精度下显示 0.0 s，但 P50/P95 桶上界均为 0.3 s，**不能据此宣称精确排队时间为零**。

## 学到什么，怎样判读

1. **命中证据和性能证据要同时出现**。只有 TTFT 下降可能混入温度、负载或启动状态；这里同一负载出现大量 prefix hit，同时客户端和服务端 TTFT 均下降，且三轮方向一致，因此支持“复用省去了重复 Prefill”的解释。
2. **改善集中在首 token，而非等比例加快 Decode**。TTFT P50 差约 0.47 s；服务端 ITL 均值只差约 0.0017 s。吞吐增加包含整批前段等待时间的缩短，不能表述为“解码速度提高 33.8%”。SSE content 事件也不保证逐 token，因此本实验没有把客户端事件间隔冒充 ITL。
3. **这不是排队或 KV 抢占实验**。当时 `max-num-seqs=8` 高于并发 4，采样无 Waiting，preemption counter 未增加，KV 使用率低。峰值采样会漏过瞬态，因而能说“未观察到瓶颈证据”，不能证明所有时刻完全无排队。
4. **高命中率有前提**。先 prime、长共享前缀、后续请求高度相似，刻意给了缓存发挥空间；不同首段或低复用业务的收益会不同。

## 验收与局限

- 验收：两组启动日志确认唯一开关；prompt 哈希和输出长度相同；预热与三轮正式分离；正式探针两组各 12/12 成功；开启组查询/命中指标与改变前缀对照方向一致；客户端和服务端 TTFT 方向一致；原始 JSON、日志和脚本可追溯。**作为 v0.18.0 探索实验，以上通过；作为 v0.29.0 B1，尚未完成。**
- 局限：固定顺序为先开后关，没有 ABBA 交叉或跨时段重复；每轮仅 4 个请求，P95 只是描述性样本分位；只有一个前缀长度和一种并发/输出分布，未测质量差异；`--enforce-eager` 关闭了 CUDA Graph/编译；当前 vLLM 0.18.0、Torch/CUDA 和旧 0.29.0 环境不同。不可宣称普适加速比或稳定服务容量。
- 收尾：两组服务均已停止，8000 端口关闭，`nvidia-smi` 显存回到约 2 MiB。
