# KV Cache dtype auto(BF16) vs FP8：vLLM 0.29.0 / RTX 4090 正式对照（2026-10-09）

> **版本边界**：这是 Phase 5 #3 的 **vLLM 0.29.0 正式实验**（驱动 590.44.01）。它与 [R570 / v0.18.0 探索性对照](kv_dtype_exploratory_r570_v018_20261008.md)是不同 vLLM 版本、不同驱动的两组数据，**不得拼接**。本页第 4 节只在"方向是否一致"这一层做对照。

## 为什么测

FP8 存 KV 的卖点是把每个 token 的 KV 字节数**减半**，从而在同显存下放更多 token。但代价是它有损：K/V 被量化到 `float8_e4m3fn`，且本版本没有校准流程（见第 3 节）。本实验在**相同 4 GiB KV 预算**下只切换 KV dtype，回答：容量是否真的翻倍、速度是否真的变快、质量是否真的不变。

## 实验条件与复现

| 项目 | 固定条件 |
| --- | --- |
| 实例 | 云端单卡 RTX 4090（49140 MiB）；驱动 590.44.01 |
| 环境 | 项目内 `.venv`：vLLM 0.29.0、PyTorch 2.13.0+cu132 |

## 正式结果

### 1) 容量：同样的字节，正好两倍 token

| 量 | auto（BF16 KV） | FP8 | 变化 |
| --- | ---: | ---: | ---: |
| KV 池 | 29,120 tokens | **58,240 tokens** | **×2.000** |
| 4096-token 请求最大并发 | 7.11× | **14.22×** | ×2.000 |
| 同负载下 KV 使用率峰值 | 0.8884 | **0.4441** | 恰好减半 |

两行都是各自启动日志实测。这不是巧合，可以逐字节算出来——Qwen3-8B 是 36 层、8 个 KV 头、head_dim 128：

```
每 token KV 字节 = 2(K,V) × 36(层) × 8(头) × 128(dim) × 字节数
  BF16: 2×36×8×128×2 = 147,456 B/token
  FP8 : 2×36×8×128×1 =  73,728 B/token
4 GiB = 4,294,967,296 B
  BF16: 4,294,967,296 / 147,456 = 29,126.9 → 向下取整到 16-token 块 = 1820 块 = 29,120 ✓
  FP8 : 4,294,967,296 /  73,728 = 58,254.2 → 向下取整到 16-token 块 = 3640 块 = 58,240 ✓
```

算出来的两个数与日志实测**逐字吻合**。

### 2) 速度：Decode 变快，Prefill 不变（3 次正式轮中位数）

| 指标 | auto | FP8 | 变化 |
| --- | ---: | ---: | ---: |
| 客户端 TTFT P50 (s) | 1.7239 | 1.8254 | +5.9%（噪声内） |
| 客户端 TTFT P95 (s) | 2.5266 | 2.5447 | +0.7% |
| 服务端 TTFT 均值 (s) | 1.6014 | 1.6240 | +1.4% |
| **输出吞吐 (tok/s)** | **188.147** | **195.317** | **+3.8%** |
| 整批耗时 (s) | 5.4425 | 5.2428 | −3.7% |
| **服务端 ITL 均值 (s)** | **0.0298** | **0.0279** | **−6.4%** |
| 服务端队列时间均值 (s) | 0.4205 | 0.4538 | +7.9%（噪声内） |

**该信哪些数字，看组间是否重叠：**

- **可信**：吞吐 auto [187.440, 188.147, 188.430] vs FP8 [195.209, 195.317, 195.393]——两组区间**完全不相交**；ITL auto [0.0296, 0.0298, 0.0299] vs FP8 [0.0278, 0.0279, 0.0282]——**完全不相交**。
- **不可信（噪声）**：TTFT P50 auto [1.7173, 1.8123, 1.7239] 与 FP8 [1.8254, 1.7423, 1.8361] **大量重叠**，中位数差 0.10 s 与组内离散约 0.09 s 同量级。只能说"方向略偏慢"，不能说"变慢了 5.9%"。

### 3) 质量：6 题全部逐字节相同

| 探针 | prompt tokens | 期望 | auto | FP8 |
| --- | ---: | --- | --- | --- |
| math | 26 | 42 | 42 | 42 |
| capital | 22 | 北京 | 北京 | 北京 |
| translation | 23 | 苹果 | 苹果 | 苹果 |
| sequence | 31 | 10 | 10 | 10 |
| long-recall-0 | **3096** | 6AFB6C38 | 6AFB6C38 | 6AFB6C38 |
| long-recall-1 | **3096** | 5D06EA96 | 5D06EA96 | 5D06EA96 |

两组 6/6 精确匹配，且**输出文本逐字节相同**。两道 3096-token 长文回忆题是这里最敏感的探针（KV 误差随序列长度累积），它们也完全相同。

**但这不是"FP8 KV 无损"的证据**，原因见下节第 3 条。

### 4) 与 R570/v0.18.0 探索结果的方向对照

| 版本 / 驱动 | BF16 KV 吞吐 | FP8 KV 吞吐 | ITL 方向 | TTFT 方向 |
| --- | ---: | ---: | --- | --- |
| v0.18.0 / R570 | 190.275 | 199.271（+4.7%） | — | 1.7856 → 1.7785（−0.4%） |
| **v0.29.0 / R590（本页）** | **188.147** | **195.317（+3.8%）** | **−6.4%** | 1.7239 → 1.8254（+5.9%，噪声内） |

两个版本上**方向一致**：FP8 吞吐小幅变好（+3.8% / +4.7%），TTFT 基本不动。这是本页唯一敢跨版本说的东西——**幅度不同、负载不同、不能互推数字**。

## 学到什么，怎样判读

1. **容量收益是确定的、可推导的，速度收益是有限的经验值。** 同样的 4 GiB，token 容量正好翻倍——这条能从"每 token KV 字节数"直接算出来，且实测吻合，不依赖负载。而速度只涨 3.8%，因为 Decode 每步的显存流量里 KV 只占一部分（权重才是大头），KV 字节减半只削掉其中一段。

2. **收益落在 Decode，不落在 Prefill。** ITL −6.4%（可信）、吞吐 +3.8%（可信），而 TTFT（Prefill 侧）在噪声内不动。这与 FP8 的作用机制一致：它压缩的是**每步要读的 KV 历史**，而 Prefill 的主要成本是处理当前这批 token。R570 组也是同样的方向。

3. **本版本的 FP8 KV 缩放是 1.0，没有校准。** Qwen3-8B 是未量化 checkpoint，权重文件里没有 K/V scale，于是走 `vllm/model_executor/layers/attention/attention.py:124` 的 `set_default_quant_scales`，把 `_k_scale`/`_v_scale` 置为 `1.0`（`:127-129`）。源码注释（`:173-178`）把这条路径写得很直白："In this case, the checkpoint does not have the scales. We need to initialize the scales to 1.0"。0.29.0 里**已经没有 `--calculate-kv-scales` 这个开关**（全仓仅剩 `vllm/models/kimi_k3/nvidia/mla.py:473` 一句注释提及）。含义是：FP8 的 e4m3 动态范围（约 ±448）没有被针对实际 K/V 分布调整过，**极端值可能被截断**。本实验测到的输入分布没有触发这个问题，但这不是保证。

4. **`--kv-cache-memory-bytes` 是一个"接管"型开关，会让 `gpu-memory-utilization` 失效。** 服务日志有一行很容易被忽略但很关键（`gpu_worker.py:544`）："reserved 4.0 GiB memory for KV Cache as specified by kv_cache_memory_bytes config and **skipped memory profiling. This does not respect the gpu_memory_utilization config.**" 也就是说本实验两组里 `gpu-memory-utilization=0.75` 对 KV 池**不起作用**了。写对照表时若不注意这点，会误以为池子大小是 0.75 决定的。

5. **右尺寸的信号：BF16 的 4 GiB 池在本负载下已经贴到 88.8%。** 8 条并发 × 3104-token 输入 = 24,832 tokens，加上最多 128 各输出 token 约 25,858，正好是 29,120 的 88.8%。**再多一条并发就必然触发抢占或排队**（实测两组 `max_waiting` 都是 4，抢占均为 0）。FP8 把这个占用压到 44.4%，等于给同样的故障点留了一倍余量。

## 验收与局限

- 两组各 8 条并发 × 3 次正式轮 = 24/24 成功且均生成 128 tokens；抢占计数两组均为 0。配置证据取自各自启动日志 `non-default args` 行，唯一差异是 `'kv_cache_dtype': 'fp8'` 这一项（auto 组该键不出现，即默认值），`'kv_cache_memory_bytes': 4294967296` 两组相同。
- 源码引用已核对：本地与云端 `vllm/model_executor/layers/attention/attention.py` 的 md5 均为 `cee5b22fcbe8561b0b8244f5d376eb3f`，版本均为 0.29.0，故行号对两侧都成立。
- **局限一：全部在 `--enforce-eager` 下完成**（无 torch.compile / CUDA Graph）。FP8 与 BF16 KV 的差距在默认模式下可能不同——eager 的额外开销会同时压低两组的绝对值。
- **局限二：固定"等字节"而非"等 token"。** 本设计回答的是"同样 4 GiB 预算，FP8 换来了什么"；若改成"同样容纳 8 条 3104-token 请求，谁更快"，FP8 就不再有池子更大的优势，比较结论会变。
- **局限三：质量只有 6 道题，且全部为确定性短答+验证码回忆。** 两道 3096-token 回忆题是现有探针里最敏感的，但**不足以外推到长文生成、领域任务或整体质量**；尤其因为第 3 条所述的缩放未校准，质量风险真实存在而未被证伪。要谈部署，需要事先固定、规模更大的质量集。
- **局限四：单一负载形状**（约 3104-token 输入 / 128-token 输出 / 8 并发 / Prefix Cache 关闭）与单一实例（单卡 4090，sm89）。sm89 上 FlashInfer 解析出 `kv_cache_dtype=torch.float8_e4m3fn`；换架构（如 Hopper 的 fp8 attention 路径）结论可能不同。
