# 权重量化 BF16 vs 官方 AWQ 4-bit：vLLM 0.29.0 / RTX 4090 正式对照（2026-10-09）

> **版本边界**：这是 Phase 5 #4 的 **vLLM 0.29.0 正式实验**（驱动 590.44.01）。它与 [R570 / v0.18.0 探索性对照](weight_awq_exploratory_r570_v018_20261009.md)**方向相反**，两组分属不同 vLLM 版本与驱动，**结论不得互推**——本页第 4 节专门讨论这个分歧。

## 为什么测

量化权重最常被期待两件事：省显存、提吞吐。省显存是确定的（权重字节数少）；**吞吐是否提高并不确定**——4-bit 权重需要反量化，kernel 是否更快取决于实现与执行模式。本实验在相同实例、相同负载、除权重外全部参数一致的前提下，测这两件事各自成立到什么程度。

## 正式结果

三类证据分开看：**显存**是确定的，**吞吐**是本实验的核心发现，**质量**只是冒烟检查。

### 1) 显存与 KV 容量

| 量 | BF16 | AWQ 4-bit | 变化 |
| --- | ---: | ---: | ---: |
| 模型加载占用 | 15.27 GiB | **5.71 GiB** | **−62.6%** |
| 加载耗时 | 40.37 s | 9.80 s | −75.7% |
| 自动 KV 池 | 143,728 tokens | **213,248 tokens** | **+48.4%** |
| 4096-token 请求的最大并发 | 35.09× | 52.06× | +48.4% |

两者都是启动日志实测。KV 池更大是"权重省下来的显存按 `gpu-memory-utilization` 转给了 KV"的直接结果。

### 2) 吞吐与延迟（3 次正式轮中位数）

| 指标 | BF16 | AWQ 4-bit | 变化 |
| --- | ---: | ---: | ---: |
| 客户端 TTFT P50 (s) | 1.8067 | 1.7727 | −1.9% |
| 客户端 TTFT P95 (s) | 2.5411 | 2.4808 | −2.4% |
| **输出吞吐 (tok/s)** | **183.872** | **172.746** | **−6.0%** |
| 整批耗时 (s) | 5.5691 | 5.9278 | +6.4% |
| 服务端 ITL 均值 (s) | 0.0300 | **0.0334** | **+11.3%** |
| 服务端队列时间均值 (s) | 0.4893 | 0.5114 | +4.5% |

离散度：BF16 吞吐 183.761 / 183.872 / 186.636，AWQ 172.742 / 172.746 / 174.252——两组各自都很稳，**组间差异远大于组内波动**，不是噪声。

### 3) 质量冒烟（6 题，两组的 prompt SHA-256 相同）

两组均 **6/6 精确匹配**（3 位数运算、常识、翻译、序列、两条长文本召回）。这**只说明这两组权重在这些小题上没有明显劣化**，不构成质量结论——没有跑 MMLU/困惑度之类的评测。

### 4) 与 R570/v0.18.0 探索结果的分歧

| 版本 / 驱动 | BF16 吞吐 | AWQ 吞吐 | 方向 |
| --- | ---: | ---: | --- |
| v0.18.0 / R570 | 189.550 | 204.312 | AWQ **+7.8%** |
| **v0.29.0 / R590（本页）** | **183.872** | **172.746** | AWQ **−6.0%** |

两组都开着 `--enforce-eager`、都关着 Prefix Cache，负载形状相近。**方向相反**，因此"AWQ 更快"或"AWQ 更慢"都不是跨版本成立的结论。

## 学到什么，怎样判读

1. **省显存是确定的，提吞吐不是。** 权重从 15.27 GiB 降到 5.71 GiB（−62.6%），KV 池相应扩大 48.4%——这条链条在 0.18 和 0.29 上都成立。但吞吐方向在两个版本之间翻转，说明它由**反量化 kernel 的实现与执行模式**决定，而不是由"权重更小"自动推出。

2. **本组的吞吐下降可以定位到 Decode。** TTFT 略微变好（−1.9%，Prefill 不受量化拖累），而服务端 ITL 均值 +11.3%（0.0300 → 0.0334 s/token）。8 条并发 × 128 tokens 的负载里 Decode 占绝对多数时间，于是整体吞吐 −6.0%。**先看 ITL 再看吞吐，才能分清是哪一段变慢。**

3. **`max_kv_usage` 是不可跨配置比较的比例。** BF16 峰值 0.1799、AWQ 峰值 0.1213，看似 AWQ 省了一半 KV——其实不是：`0.1799 × 143,728 ≈ 25,857` tokens，`0.1213 × 213,248 ≈ 25,867` tokens，**绝对占用基本相同**。同一条负载，池子变大，比例自然变小。任何只看 `kv_cache_usage_perc` 就下结论的对照都会在这里踩坑。

4. **量化收益要用"每 token 成本"而不是"能不能跑"来衡量。** 如果业务受显存限制（大模型装不下、长上下文要更大 KV 池），AWQ 用 6% 吞吐换 48.4% KV 容量可能是划算的；如果显存充裕，本配置下它是净亏。

## 验收与局限

- 两组各 8 条并发 × 3 次正式轮 = 24/24 成功且均生成 128 tokens；配置证据取自各自启动日志 `non-default args` 行（`'quantization': 'awq_marlin'`、模型目录、`enable_prefix_caching: False`、`enforce_eager: True`）。
- **局限一：全部在 `--enforce-eager` 下完成**（关闭 torch.compile 与 CUDA Graph）。这本就是最可能影响量化 kernel 表现的口径——**未测的对照正是"默认模式（CUDA Graph + torch.compile）下 AWQ 是否反超"**，这是本页最直接的后续实验。
- **局限二：单一负载形状**（约 3100-token 输入 / 128-token 输出 / 8 并发 / Prefix Cache 关闭）。输入更短或输出更长的负载会改变 Prefill/Decode 占比，结论可能不同。
- **局限三：质量只有 6 道冒烟题、且全是短答精确匹配**，不足以外推；未做困惑度或标准评测集。
- **局限四：跨版本分歧未定位到具体代码差异。** 本页只如实记录方向相反，不宣称知道 v0.18.0 → v0.29.0 之间哪一次改动导致了它。
