# KV Cache 容量与 Preemption 对照实验

记录日期：2026-09-23。

## 结论

同一台 RTX 4090 48GB、同一 Qwen3-8B、同一组 8 并发请求，在正常 KV 池中连续 3 次都没有排队或抢占；把 vLLM 管理的 KV block 数受控限制为 1024 后，连续 3 次都出现了 1 次 Preemption。受控组没有 OOM，24/24 请求全部成功，但每批都有一条请求出现约 2.86–3.17 秒的流式输出停顿，整批吞吐量中位数下降约 6.1%。

这组结果形成了“KV 使用率接近上限 → Running 从 8 降为 7、Waiting 变为 1 → Preemption counter 增加 → 被抢占请求流式停顿并晚完成 → 整批吞吐量下降”的证据链。它也说明：只看全局 ITL P95 会掩盖单条被抢占请求的长停顿。

## 环境与单变量设计

- GPU：NVIDIA GeForce RTX 4090，49140 MiB；驱动 590.44.01。
- PyTorch：2.13.0+cu132；CUDA 可用；vLLM 0.29.0。
- 模型：Qwen3-8B，BF16；36 层、8 个 KV heads、head dimension 128。
- 模型路径：云端 `/root/fsas/vllm-lab/models/Qwen3-8B`。
- API：只监听云端 `127.0.0.1:8000`；Mac 经 SSH 本地转发访问 `127.0.0.1:18000`。
- 两组共同配置：`max-model-len=4096`、`gpu-memory-utilization=0.75`、`block-size=16`、`max-num-seqs=8`、`max-num-batched-tokens=4096`、chunked prefill、prefix caching、`scheduler-reserve-full-isl`、`watermark=0`。
- 唯一关键变量：受控组增加 `--num-gpu-blocks-override 1024`。

正常组启动日志给出的 KV 容量为 137360 tokens，对 4096-token 满上下文的理论容量为 33.54x。受控组把自动分析出的 8967 blocks 覆盖为 1024 blocks，容量变为 16384 tokens、理论满上下文容量为 4.00x。完整启动日志分别保存在 [正常组服务日志](kv_server_normal_20260923-185707.log)和[受控组服务日志](kv_server_constrained_20260923-190333.log)。

按模型结构估算，每个 token 的 BF16 KV 为：

```text
36 layers × 2(K/V) × 8 KV heads × 128 head_dim × 2 bytes
= 147456 bytes
= 144 KiB/token
```

因此每个 16-token block 约保存 2.25 MiB KV。此公式适用于这次 Qwen3-8B 的均匀全注意力结构；混合注意力模型应以 vLLM 的 group-aware 启动容量为准。

## 固定负载

- 每批通过 Barrier 同时提交 8 个请求。
- 每个请求实际输入 173 tokens。
- 每个请求固定生成 2048 tokens，`min_tokens=max_tokens=2048`、`temperature=0`、关闭思考。
- 每组先做一次 1 请求、64 输出 token 的预热，再做 3 次正式重复。
- 每个正式批次总输出 16384 tokens，预期 `finish_reason=length`。
- 每组每次 prefix cache queries 为 1384 tokens、hits 为 240 tokens，来自聊天模板和同批公共开头；两组相同，因此没有形成组间缓存偏差。

在所有 8 条请求接近完成时，未经共享折算的总上下文约为：

```text
8 × (173 prompt + 2048 output) = 17768 tokens
```

这只占正常池约 12.9%，但超过受控池的 16384-token 容量。由于 `scheduler-reserve-full-isl` 在准入时检查完整输入，而不是预留所有未来输出，8 条短输入起初都能进入 Running；随后 Decode 不断增长才触及 KV 边界。这正是本实验希望观察的情形。

## 指标如何互相验证

1. 正常组的 Running 峰值为 8、Waiting 为 0、KV 峰值约 12.8%、Preemption 为 0，证明该负载没有触及正常容量。
2. 受控组客户端以 0.1 秒间隔采样到 KV 峰值 99.5%–99.9%、Waiting 峰值 1；云端周期日志也两次记录到 `Running: 7 reqs, Waiting: 1 reqs`，当时 KV 使用率为 93.0% 与 89.1%。
3. Prometheus `vllm:num_preemptions_total` 在三批中每次增加 1，服务停止前累计值为 3。这是引擎记录真实抢占的直接证据。
4. 云端周期日志没有打印 `Preemptions:` 字段，因此本次不把“日志中未出现该字段”解释为没有抢占；应以 counter 增量为准，并用 Running/Waiting/KV 状态和请求级停顿交叉验证。
5. 服务端 queue-time histogram 的总和仍只有约 0.0002–0.0003 秒，但它不能测量抢占后的再次等待。vLLM 0.29.0 的 metrics 源码把 queue time 定义为首次 `QUEUED` 到首次 `SCHEDULED`，并明确忽略 Preemption 后的后续 `SCHEDULED` 事件。因此这项 histogram 只能说明初次准入几乎没有排队，不能据此拆分约 3 秒停顿中的再次等待与重复计算。

## TTFT 与 ITL 为什么变化不大

抢占发生在请求已经开始流式输出之后，所以大多数 TTFT 不应受它影响。受控组第二次客户端 TTFT 明显偏高，但服务端 TTFT 没有一致同向变化，因此不能把这次端到端波动全部归因于 GPU 或 Preemption。

全体请求的内容块间隔 P95 也只从约 0.0412 秒变为 0.0425 秒，因为 8 条请求、每条 2048 个内容事件中，只有一条请求出现一次约 3 秒停顿。这个少数尾部事件会被全局 P95 淹没。判断 Preemption 对用户体验的影响时，应补看“每请求最大停顿”和请求完成时间分布。

正常组第一次正式运行还记录到 `_gumbel_sample_kernel` 的推理期 JIT 警告，且该次最大单请求间隔为 0.5969 秒；后两次为 0.1035 与 0.0731 秒。这说明小预热没有覆盖 8 请求形状，也说明保留三次重复和服务日志是必要的。

## 局限

- 受控组是人为缩小 vLLM 逻辑 KV 池，用于安全验证机制；它不代表这张 48GB 4090 的正常容量。正常配置下同一负载只使用约 12.8% KV。
- 两组各正式运行 3 次，足以说明该负载下的可重复机制现象，但不是生产容量规划。
- 客户端内容块间隔受 SSH 和 SSE 缓冲影响，不是严格逐 token ITL；服务端 histogram 是批次级聚合，也无法指认具体被抢占请求。
- Prefix cache 并非完全为零，但两组的查询和命中增量相同。若以后精确测量纯 KV 容量，可进一步消除公共用户前缀或关闭 prefix caching，届时需要作为新的单变量实验记录。
- 实验没有制造 OOM，也没有提高到多次反复抢占；首次可重复抢占已足以完成本模块验收。

实验结束后已停止 vLLM 服务，远端检查无残留 `vllm`/`api_server` 进程，GPU 显存回到 1 MiB used；SSH 本地转发和登录会话也已关闭。云实例是否停止计费仍需以 Vylai 控制台状态为准。
